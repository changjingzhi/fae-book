# 产品边界意识

> **归档信息**：What 素材（核心方法论）· 用户提供 · 2026-10-16 整理（格式整理版，文字保持原样；含 IQ9075 32 路解码、8K HEVC 等真实实例）

## 作为 FAE，如何明确知道公司产品的边界？

作为 FAE，要明确知道**公司产品的边界**，核心不是把产品手册背下来，而是建立一套「**什么能做、做到什么程度、什么不能做、超出以后谁负责**」的判断体系。

结合 Aidlux / X1 / 9075 / QCS8550 / QCS6490 这类端侧 AI 产品，产品边界可以理解成下面几个层次。

### 1. 先区分：规格 ≠ 能力 ≠ 交付能力

这是 FAE 最容易混淆的地方。比如：

> 芯片规格：支持 32 路 1080p30 解码

不等于：

> 我们的盒子一定能稳定跑 32 路 1080p30。

更不等于：

> 客户的 32 路视频 + AI 推理 + 编码 + 显示 + 网络场景都能跑。

中间至少还有六层能力：
**芯片理论能力 → BSP/驱动能力 → SDK/GStreamer 能力 → 板卡实际能力 → 整机稳定能力 → 客户完整业务场景能力**

**实例：IQ9075 的 32 路解码测试**

- 规格写 32 路，不代表 FAE 就可以直接对客户承诺："我们实测支持 32 路。"
- 实际测试：24/25 路稳定，26 路出现异常/重启
- 正确的边界表述：**芯片规格支持 32 路，但当前产品软件/散热/系统配置下，实测稳定能力需要进一步验证。**

这就是 FAE 的边界意识。

### 2. 给每个产品建立一张「能力边界表」

以后客户问问题，不要从记忆里回答，而是往这张表里套。

| 维度 | 需要明确什么 |
| --- | --- |
| 硬件 | CPU / GPU / NPU / VPU / 内存 / 存储 / 接口 |
| 编解码 | 支持什么格式、分辨率、帧率、并发 |
| AI | 支持哪些模型、框架、精度、算力 |
| 软件 | OS、BSP、SDK、驱动、GStreamer |
| 性能 | 官方规格 vs 实测数据 |
| 稳定性 | 连续运行多久、什么负载 |
| 交付 | 公司是否有现成方案 / 代码 / 技术支持 |
| 定制 | 哪些能改、哪些需要研发 |
| 商务 | 是否涉及额外报价 / 项目立项 |

尤其最后三个（交付 / 定制 / 商务），是**售前 FAE 非常重要的边界**。

### 3. 把能力分成 4 个等级

- **A 级：已经产品化** —— 可以直接告诉客户："支持。"
- **B 级：理论支持，但没有完整验证。**
  例如：芯片规格支持 8K HEVC；V4L2 能识别 HEVC；`/dev/video32` 可以设置 7680×4320；但实际 GStreamer 8K 60fps 解码最初出现 `not-negotiated`。
  这种时候不能直接说"支持 8K 60fps"，应该说：**底层硬件/驱动具备对应能力，目前正在验证具体软件链路和稳定性。**
  这属于：**理论能力 ≠ 已验证产品能力。**
- **C 级：可以做，但需要研发支持。**
  例如客户说："我要在 X1 上集成一个 ModelFarm 里没有的模型。"
  你可能知道 ONNX 可以转、QNN 可以跑、Aidlite 有接口——但这并不意味着"你给我模型，我马上就能交付"。可能涉及：
  **模型转换 → 算子适配 → QNN 编译 → 性能调优 → SDK 集成 → Demo → 测试**
  这时候应该判断：**技术上可能可行，但属于项目支持/研发工作，不属于标准产品能力。**
  然后进入：**商务报价 / 研发评估 / 项目立项。**
- **D 级：产品边界之外。**
  比如客户提出："你们这个 9075 能不能直接做完整汽车大模型座舱？"
  这时候即使芯片理论上有 NPU，也不能因为"能跑模型"就回答"可以"。因为完整汽车大模型座舱涉及：SoC、OS、多媒体、AI、LLM/VLM、语音、Agent、车控、ECU、中间件、HMI、车规认证、整车适配——这已经不是单纯的芯片/板卡能力问题。
  正确的动作是：**拆解需求 → 找出公司能提供的部分 → 找出第三方/客户需要负责的部分 → 判断是否需要商务和研发介入。**

### 4. FAE 最重要的一句话：不要把「芯片能力」当成「公司承诺」

> **芯片支持 ≠ 板卡支持 ≠ SDK 支持 ≠ Demo 支持 ≠ 产品支持 ≠ 项目交付。**

### 5. 回答客户问题时，最好永远带「证据等级」

- **「规格支持」**：来源是芯片/产品 Datasheet，代表**理论规格**。
- **「软件支持」**：来源是 SDK / BSP / 驱动 / API / 官方 Demo，代表**软件栈已经提供能力**。
- **「已验证」**：来源是自己测试过，代表**在明确测试条件下成立**（例如：1920×1080 / H.265 / 25fps / 单路 / fakesink）。
- **「稳定支持」**：来源是长时间、目标负载、目标环境测试（例如：32 路 × 1080p30 × 8 小时）。这个才比较接近客户真正关心的：**能不能拿去做产品。**
- **「项目支持」**：代表技术上存在可能性，但需要研发投入。
- **「定制开发」**：代表已经明显超过标准产品能力。

### 6. 判断流程

```
客户需求
   ↓
公司产品有没有这个功能？
   ↓
 ┌───────────────┐
 │               │
有               没有
↓                 ↓
规格支持？       芯片理论上能不能做？
↓                 ↓
软件支持？       可以？
↓                 ↓
实测验证？       需要研发？
↓                 ↓
稳定性验证？     商务报价？
↓
可以直接承诺
```

### 小结

FAE 真正需要建立的不是"我知道公司产品有什么"，而是：

> **"我知道什么情况下我可以说『支持』，什么情况下只能说『理论支持』，什么情况下必须找研发，什么情况下必须走商务流程。"**

这其实就是**产品边界感**。

而且对偏 **售前 FAE + AI 模型 + 性能测试 + 项目交付** 的岗位来说，这个能力甚至比单纯会调 Linux、会跑模型更重要。最终要成为的，是那个能把客户一句"能不能做"，拆成**产品能力、技术风险、验证工作量和商务范围**的人。
